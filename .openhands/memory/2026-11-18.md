## The profit model (why any target is provable)
`NetProfit = N·Σ(y_i − f_i) − gas`, gas=0 (protocol-sponsored). N is the
uncollateralised flash capital. A path with no flash primitive pins N=0 and
cannot earn — the prover enforces this via `AtomicPath.has_uncollateralized_capital`.
YIELD_BANDS start at 3x the FEE_BANDS ceiling so each hop's net rate stays
positive even after the prover's ±20% relaxation. MAX_NOTIONAL_USD = 1e9.

## Session 2 — four surfaces, four different profit numbers

### Root cause worth remembering
The solver picks concrete `y_i`/`f_i` values *inside* each band; the composer
declares only the band centre. The loop aligned `path.notional_usd` to the
witness `N` but **not** the per-step rates, so:

- narrative / certificate → `witness["net_profit_usd"]`
- executor + UI footer   → `path.notional_usd * path.net_rate`

diverged by ~5% (live: 171,875.00 vs 181,752.41). Fix: `AtomicPath` gained
`proven_net_profit_usd` (set from the witness, preferred by the property), and
`_align_to_witness` copies `N` and every `y_i`/`f_i` onto the path. Rounding
`net_rate` to 8dp is what made a pure rate-recompute still drift by 4e-6
relative — the certified scalar is the only safe single source.

**General lesson:** when a solver returns a witness for a symbolic model, the
witness is the truth; any value recomputed from the declared inputs is a
different number wearing the same name.

### GitHub search quota
`/search/repositories` is 30 req/min for an authenticated token, and the
scanner fires 9 queries + 1 RPC feed. Burning it silently is easy: the query
had no `pushed:>` qualifier, so `sort=updated` returned mostly stale repos that
the 48h post-filter then dropped *after* the quota was spent. Adding
`pushed:>YYYY-MM-DD` to the query took one probe from 0 → 11 fresh repos.
A 403/429 now sets `scan_rate_limited` (1h window), surfaced by `/status` and
in the narrative. `POST /primitives/refresh` re-scans on demand.

**Environment note:** secrets are injected per-command, so a server started in
one command does not inherit `GITHUB_TOKEN` for later requests unless it is
exported at launch. `pkill -f "uvicorn synthesizer.api"; GITHUB_TOKEN=$GITHUB_TOKEN nohup python3 -m uvicorn ... &`.

### Vacuous certificate
`prove_bound(constraints, None)` produced an empty band → trivial UNSAT →
`max_atomic_profit=0.00 USD` next to `N_max=1e9`. That reads as a market fact
but is a statement about a missing path. Now returns `detail="no_path"` with
"no market ceiling was measured", and the loop bounds over the best real
composition (live: 5,410,000.00 USD).

- Etherspot → 400 invalid API key. Stackup/Gelato/Biconomy → ConnectError.

**Network rungs:** Base Sepolia primary, **Arbitrum Sepolia** fallback. Do NOT

**The ERC-4337 bugs that look like dead paymasters (all cost real debugging):**
- `AA20 account not deployed` → the account must be counterfactual + `initCode`.
- `AA14 initCode must return sender` → never hash local factory calldata; call
  factory `getAddress(address,uint256)` on-chain for the authoritative address.
- `AA23 ECDSA: invalid signature` → the userOp hash MUST cover every gas field
  AND `paymasterAndData`, and signing must be **two-phase**: sign → sponsor →
  re-sign over the paymaster's returned gas fields. A hash missing gas fields
  signs a different op than the one broadcast. Locked by
  `test_userop_hash_covers_every_gas_field`.

**Latency contract vs real settlement genuinely conflict** (~90ms proof vs ~2.4s
settlement). Resolution: prove synchronously, settle in a `ThreadPoolExecutor`,
upgrade the stored `IntentResult` in place; `GET /intent/{id}` exposes the
upgrade and the web UI polls it. Do not block `/synthesize` on settlement.

**The remaining hard cap — value, not gas.** Gas is sponsored; value is not.
The smart account holds 0 ETH on every chain, and conservation of value is not
something the engine can override. So `value_transferred` is computed only
after an on-chain balance check (`GasFlywheel.balance_of`) and is `false` today.
The honest claim is "executed, gas paid by a sponsor, no funds moved" — the
engine must never imply a payout that did not happen.

# 2026-11-18 — the settlement path finally pays, repeatedly

## Root cause of "prove but can't deliver" (commit `de447b9`)
`composer.propose()` / `propose_deep()` / `templates.py` all set
`intent_id=constraints.beneficiary` — a CONSTANT address. `GasValueLock` guards
`settled[intentId]`, so the FIRST settlement consumed the key and every later one
reverted inside the lock while its transaction still mined with status 1. Verified
on chain: `settled(keccak(beneficiary)) == 1`. The API path therefore always showed
`REVERTED_VALUE` / delivered 0.0; a direct `ex.settle()` call worked only because it
happened to be the first.

Fix: the loop stamps the real intent id on the chosen path after witness alignment
(`chosen.intent_id = iid`); composers no longer seed the beneficiary; new
`executor._settlement_key(path)` gives an id-less path a stable, distinct sha256 key.

Second fault: `propose_deep` never set `proven_net_profit_usd`, so
`settlement_call_data` encoded `execute(beneficiary, 0, "0x")` — an empty call that
mines clean, spends sponsor gas and pays nobody. Now the deep path carries
`notional*net_rate`, and `settle()` refuses a path with no proved amount
(`status="queued"`, `reason="no_settlement_amount"`).

## Self-funded AA is now a fact, not a claim (commit `e5a7bbc`)
Proved `handleOps` execution end-to-end against the REAL EntryPoint 0.8.0 +
SimpleAccountFactory bytecode in a local py-evm chain — no paymaster, no bundler.
Three real bugs were hiding behind the claim, all only visible against real
bytecode:

1. **AA24 signature error = chain-id mismatch.** py-evm's `CHAINID` opcode
   defaults to `131277322940537`, NOT the 1337 the RPC advertised. The EntryPoint
   folds chain id into the userOp hash domain separator, so the client signed a
   different digest. Diagnose by comparing our `user_op_hash` with the
   EntryPoint's own `getUserOpHash` via `eth_call` — they must be byte-identical.
   Fix: `tests/localchain.py` now advertises `backend.chain.chain_id`.
   (`MiningChain.configure(..., chain_id=...)` + `PyEVMBackend(vm_configuration=...)`
   works too, but advertising the real id is simpler.)
2. **AA13 initCode failed or OOG = deploy gas.** Deploying a SimpleAccount costs
   ~299k verification gas; the default budget was 200k. Now `DEPLOY_VERIFICATION_GAS
   = 400_000` when `initCode` is non-empty.
3. **AA95 out of gas = outer tx limit too small.** The outer `handleOps` tx must
   cover `verificationGas + callGas + preVerificationGas` plus ~330k of
   EntryPoint bookkeeping (measured: 978k actual for a 650k inner budget).
   `HANDLE_OPS_OVERHEAD_GAS = 400_000`.

Debug technique that made this tractable: `FailedOp(uint256,string)` selector is
`0x220266b6`. eth-tester *stringifies* revert bytes as `b'...'`, so use
`eval(msg)` to recover them before `eth_abi.decode`. Also: `deploy()` needs
12M gas for the EntryPoint (5.3M used) — a low limit reports as failure, not OOG.
